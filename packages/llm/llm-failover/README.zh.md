# `@deepseek-ai/dsh-llm-failover`

[English](README.md) | 中文

## 概述

在 agent 循环的 `agent/request-error` 恢复瀑布上实现跨提供方故障转移。额度耗尽的提供方同样无法服务下一次尝试，重试它并不是恢复；本插件把重试改道到下一个已配置的提供方，并让耗尽的那个进入冷却。这正是一个人把工作分散到多个账号的免费额度上、而不必盯着某一个何时用尽的前提。

<a id="composition"></a>
## 组合关系

它组合在 [`dsh-llm-retry`](../llm-retry/README.zh.md) **之下**，而非取代它。retry 负责「同一个提供方，稍后再试」，并对自己修不了的失败放行；凡是它放行的都会到达这里。这个分工来自失败分类本身，而不是两者之间的任何协调：

| 失败 | retry | failover |
|---|---|---|
| `QUOTA` | 不在其默认可重试集合中，立即放行 | 立刻改道 |
| `RATE_LIMIT` | 在同一路由上花完退避预算 | 预算用尽后改道 |
| `MISSING_CREDENTIAL` | 放行 | 改道 —— 这份安装本就没有该路由 |
| `AUTH`、`INVALID_CREDENTIAL` | 放行 | 同样放行 —— 请求失败 |

先挂载 retry，让它占据瀑布的外层。单独挂载 failover 也是合法的，那样会在第一个符合条件的失败上直接改道。

<a id="config"></a>
## 配置

| 字段 | 必填 | 说明 |
|---|---|---|
| `order` | 否 | 依次尝试的提供方/模型组合；处于冷却的条目会被跳过。为空（默认）时不做任何改道。 |
| `cooldownMs` | 否 | 非额度类失败后跳过该路由的时长（默认 300000） |
| `quotaCooldownMs` | 否 | `QUOTA` 后跳过该路由的时长（默认 3600000） |

```yaml
- name: '@deepseek-ai/dsh-llm-failover'
  config:
    order:
      - provider: deepseek
        model: deepseek-chat
      - provider: qwen-token-plan-cn
        model: qwen-plus
```

每个条目自带模型，因为模型 id 属于服务它的提供方；不存在两个路由都认识的 id。

同样这几个字段也是 `llm-failover` 命名空间下的 **settings 区段**，因此上面的组合条目是部署默认值，而使用者可以在「设置」里改动生效中的顺序、无需碰任何文件。已经生效的冷却不受编辑影响：重排列表并不会让耗尽的额度回满。

<a id="what-it-reroutes"></a>
## 会改道哪些失败

只包括另一个提供方确有可能服务的类别：`QUOTA`、`MISSING_CREDENTIAL`、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT`。其中多数描述的是某一个提供方在某一刻的可用性，而这恰恰是另一个提供方并不共享的东西。

两种凭据类失败被刻意区分，因为它们的修法不同。`MISSING_CREDENTIAL` 意味着从未提供过密钥 —— 该路由本就不属于这份安装，跳过它正是部署方得以预置一份「比任何单个用户实际注册的都多」的顺序的前提。而被*拒绝*的密钥（`AUTH`、`INVALID_CREDENTIAL`）是一个有明确修法的配置错误，若悄悄改用另一个账号来服务请求，只要还有别的路由可用，这个错误就会一直被掩盖 —— 使用者永远不会知道自己选的提供方配错了。

`order` 未收录的路由不受干预：它是被刻意选择的，未经请求就改道等于覆盖那个选择。当所有路由都在冷却时，失败保持终结，而不是拿一个已知有问题的提供方去重试。

冷却不是降级。冷却期一过，首选路由重新成为首选 —— 这正是每日免费额度得以运转的方式：额度用尽，当天余下的工作转移出去，而第二天的第一个请求又回到首选。冷却状态存于内存，因此重启后会回到第一个路由，并以一次失败尝试的代价重新学到。

<a id="durable-record"></a>
## 持久记录

每次改道都会向会话追加 `llm/failover`：失败的路由、接手的路由及其模型、冷却时长，以及提供方中立的失败事实。没有它，提供方的切换就是不可见的，而一个始终不知道首选已经耗尽的人也就无从应对。[不变量伴生插件](src/invariant.ts)在持久化边界校验每一条记录。

<a id="model-experience"></a>
## Model Experience

### 被改道的模型请求

#### 模型看到什么

看不到改道本身：重试的请求携带同样的消息、系统提示与工具。服务它的模型换了一个，因此回复反映的是第二个提供方的模型而非第一个。

路由接手时会丢弃推理强度。提供方接受哪些级别是它自己的事，把一个级别带过去，可能被一个从未提供过该级别的模型直接拒绝。

#### Token 影响

无直接影响；改道后的请求就是原来那个请求。生效的是服务方模型自身的分词器与上下文核算。

#### KV Cache 影响

改道会放弃前缀缓存。第二个提供方从未见过这段对话，因此无论前缀在第一个提供方上多么稳定，它的首个请求都是完全未命中。之后的步骤在新提供方上正常预热，直到冷却结束、首选路由回归 —— 那时会再放弃一次。

<a id="known-limitations-and-deferred-work"></a>
## 已知限制与后续工作

- **冷却是进程内的** —— 不做任何持久化，因此重启后会再次重试一个已耗尽的提供方，之后才重新学到；共用一个账号的两个宿主也不共享彼此学到的东西。
- **没有主动的额度核算** —— 只能通过失败才知道某个路由已耗尽。在提供方开口之前，插件无法知道免费额度即将用完。
- **顺序是静态的** —— 条目按给定顺序尝试，没有基于健康度的重排或加权，也没有同一提供方内部的逐模型回退。

## 开发备注

<details>
<summary>面向维护者的工作上下文 —— 点击展开</summary>

本开发备注不具权威性，只是维护者的工作笔记与开放问题。已交付的行为与已接受的理由在上面各节、包代码以及关联的 Agent Note 中。

- base 组合包把这一行挂在 `llm-retry` 之后，这正是它位于 retry 内层的原因。分工完全来自失败分类本身，无需任何协调：`QUOTA` 不在 retry 的默认可重试集合里，会直接放行到这里；`RATE_LIMIT` 在集合里，所以 retry 会先花完自己的退避预算。集成测试把这个序列锁定为 `['mock','mock','mock','other']`。
- 另一半在 `agent/request` 上用 `prepend: true` 占据最外层，覆盖 agent 作用域的模型选择（cordis 瀑布是最外层优先）。重试会重新进入 `agent/request`，但**不会**重新进入 `system-prompt/assemble`，所以只改 `selection.current` 是无效的。
- `MISSING_CREDENTIAL` 会切换，而 `AUTH` 与 `INVALID_CREDENTIAL` 不切换：从未提供过的密钥意味着该轮到另一条路由，而配置错误的密钥必须暴露出来。正是这个区分，让部署可以预置一份比任何单个用户注册得都多的顺序。
