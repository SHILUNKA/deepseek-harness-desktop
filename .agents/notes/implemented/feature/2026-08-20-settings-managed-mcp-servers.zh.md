# Agent Note: 由设置管理的 MCP 服务器

Status: implemented

[English](2026-08-20-settings-managed-mcp-servers.md) | 中文

## 问题

MCP 服务器是一个插件实例而非一个值，因此添加一个就意味着往组合里写入一行。对使用桌面应用的人来说，这是在获得单个工具服务器之前要先学会的三件彼此独立的事：该改哪个文件（`~/.dsh/cordis.patch.yml`，位于 Finder 默认隐藏的点目录中）、这个文件使用的补丁方言，以及要在其中写出的插件包名。而产品里没有任何地方提到 MCP 是可配置的 —— 设置里提供了「模型」「插件」和一份只读的插件列表，它们都无法挂载任何东西。

## 决策

`@deepseek-ai/dsh-mcp-servers` 在一个 settings 区段（`mcp-servers`）中持有服务器列表，并为每个启用的条目挂载一个 `mcp-client` 实例，在每次变更时进行调谐。增删一个服务器是一次设置写入；组合不参与其中，也不需要重启。

部署自带的服务器仍以各自的组合行存在且不受影响 —— 管理器只拥有它自己的区段。

调谐先卸载再挂载，并等待每次卸载完成。名字在 fiber 释放时即被交还，因此替换无论如何都不会被拒绝；等待所换来的，是旧的子进程在其替代者启动之前已经退出 —— MCP 服务器可能持有某种独占资源。多次调谐被串行化，因此两次快速编辑不会都基于同一份过期的已挂载视图行事。

被拒绝的条目只付出它自己的代价。Schemastery 在构造时即完成校验，而 `mcp-client` 在激活期间保留其命名空间，因此拒绝可能是同步到达的；捕获之后记录并跳过，本轮其余条目继续。管理器还会自行调谐一次，而不是只在被通知时才动，因为 `installSettingsSection` 是通过一次 settings 注入来通知的 —— 一个组合了服务器却没有挂载 settings 提供方的部署，否则将永远收不到第一轮，也就一个服务器都不会运行。

浏览器侧是「设置 → 插件」下的一张卡片，每行编辑一个服务器，格式为 `名称: 命令 参数`，行首 `#` 表示保留但不运行。

## 曾考虑的替代方案

**做一个读写 `cordis.patch.yml` 中 MCP 行的 Host API，并在其上做设置页。** 这是最初的方案，补丁层热重载也正是为它落地的（`feat(desktop): keep user patch layers live`）。在意识到管理器可以直接持有这些实例之后，它被放弃了：从界面写一种补丁方言意味着要拥有一个文件格式、一个插入位置和一套合并说法，而挂载一个插件只需要拥有一个 `Map`。热重载依然正确且有用，可用于手工编辑；这条路不再需要它。

**用文本域而非每个服务器一行控件。** 启动命令是人们从 README 整段粘贴的东西，而按参数拆分的表单会迫使他们先把它拆开。每服务器一行控件是最终形态；解析在遇到格式错误时拒绝而不是丢弃服务器，因此无论如何存储的值都保持可信。

**在卡片上报告连接状态。** 推迟。受管服务器是否真的连上了，是一个本包并不呈现的 Host 事实；今天由 Loader 的插件清单来回答。增加一条状态通道是另一项改动。

## 结果

一个人可以在不知道组合、补丁文件或 `@deepseek-ai/dsh-mcp-client` 存在的情况下添加一个 MCP 服务器，也无需重启应用。

代价：只有 stdio 服务器能以这种方式配置 —— HTTP 服务器、`env`、`cwd`、超时与重连策略仍然只属于组合层，受管条目在这些方面采用 `mcp-client` 的默认值。卡片报告的是「配置了什么」而非「谁在服务」，因此一个命令写错的服务器会保存成功，随后在日志里失败。改动列表会改变工具 schema，因此编辑后的第一个请求是一次前缀缓存未命中。

## 测试

`packages/mcp/mcp-servers/tests/managed-servers.spec.ts` 以一个真实的 stdio MCP 服务器作为 fixture，并通过工具注册表进行断言：一次设置写入获得一个服务器、移除会失去它、被禁用的条目从不运行、命令改变的条目会被替换（fixture 按参数为其工具命名，因此「从未挂载成功的替代者」是可观测的）、未变的条目在另一个被编辑时继续运行、被拒绝的条目不会拖垮其他条目，以及在没有 settings 提供方时组合列表照常运行。最后两个用例各自发现了一个真实缺陷 —— 同步拒绝会中断本轮其余部分，以及组合列表永远收不到第一轮。
