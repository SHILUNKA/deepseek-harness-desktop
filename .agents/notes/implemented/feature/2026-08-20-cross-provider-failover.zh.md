# Agent Note: 跨提供方故障转移

Status: implemented

[English](2026-08-20-cross-provider-failover.md) | 中文

## 问题

若干提供方都发放每日或每月的免费额度，而单个额度很少能撑满一天的 agent 工作。额度用尽时提供方回答 `QUOTA`，而 harness 对这个回答无能为力：`dsh-llm-retry` 实现的是*同一提供方*重试，因此它只会等待后再次询问同一个已耗尽的账号；何况 `QUOTA` 根本不在它的默认可重试集合里 —— 失败径直抛给用户，成为一个死掉的回合。一个持有四家提供方密钥的人，只能自己察觉失败、打开设置、手动切换模型，一天数次。

## 决策

`@deepseek-ai/dsh-llm-failover` 把失败的请求改道到下一个已配置的提供方，并让失败的那个进入冷却。

它组合在 `agent/request-error` 瀑布上 `dsh-llm-retry` 的**下方** —— 在 `packages/bundle/base/cordis.patch.yml` 中挂载于其后，按 Cordis 由外向内的顺序，这使 retry 成为外层。两者之间不存在也不需要任何协调，因为失败分类本身已经把它们分开：`QUOTA` 不在 retry 的默认可重试集合中，会立即到达 failover；而 `RATE_LIMIT` 只有在 retry 于同一路由上花完退避预算之后才会到达。

另一半以 `prepend: true` 安装在 `agent/request` 上，占据最外层位置，从而能够替换 agent 作用域的模型选择所做的决定。这是必需的而非风格偏好：重试会重新进入 `agent/request`，但**不会**重新进入 `system-prompt/assemble`，而 `installModelSelection` 应用的是 `selection.assembled` —— 在组装时捕获的值 —— 因此改动其他任何东西都无法存活到被重试的请求中。只要解析出的提供方不在冷却中，该监听器就不做任何事，所以一个明确的选择在它仍然可用时绝不会被覆盖。

凭据类失败按其修法而分。`MISSING_CREDENTIAL` 会改道：从未提供过密钥，说明该路由本就不属于这份安装，跳过它正是部署方得以预置一份「比任何单个用户注册的都多」的顺序的前提。`AUTH` 与 `INVALID_CREDENTIAL` 则不会：被拒绝的密钥是一个配置错误，若悄悄改用另一个账号来服务，只要还有别的路由可用，这个错误就会一直被掩盖。

改道时会丢弃推理强度 —— 提供方接受哪些级别是它自己的事，把一个级别带过去可能被直接拒绝。

每次改道都会向会话追加 `llm/failover`，因此提供方的切换是可见的而非无声的；顺序本身是一个 settings 区段（`llm-failover`），在「设置 → 插件」下有对应的卡片。

## 曾考虑的替代方案

**包装 `ctx.llm.stream()`。** 出于 `dsh-llm-retry` 已记录的同一理由而否决：每次适配器调用都应保持为一次提供方尝试，且每次重试在日志中开启自己的编号回合。包装器会把第二个提供方的尝试藏在第一个的回合里。

**在已经拥有 `ModelSelectionRef` 的 `api-proxy` 中切换。** 那样可以直接触及可变的选择，也无需任何瀑布位置 —— 但它是 web/desktop 的入口点，于是 CLI 将无法从一个本不特定于传输方式的能力中获益。

**永久切换而非冷却。** 冷却会过期，这正是*每日*额度得以运转的方式：额度用尽，当天余下的工作转移出去，而第二天的第一个请求又回到首选。降级则会让首选提供方在一个糟糕的下午之后被无限期闲置。

**预置一份默认顺序。** 否决：顺序条目需要模型 id，而模型 id 按提供方的时间表变化，而非本仓库的。组合层默认值为空，列表由设置填入。

## 结果

一个人可以在一天内花掉多家的免费额度，而不必盯着某一家何时耗尽；切换会被记录而不是无声发生。

代价：冷却是进程内的，因此重启后会再次重试一个已耗尽的提供方，之后才重新学到；共用一个账号的两个宿主也不共享彼此学到的东西。改道会放弃前缀缓存，因为第二个提供方从未见过这段对话。顺序是静态的 —— 没有基于健康度的重排、没有加权、也没有同一提供方内部的逐模型回退。在提供方真正失败之前什么也学不到：不存在主动的额度核算。

## 测试

`packages/llm/llm-failover/tests/failover.spec.ts` 覆盖额度改道、持久记录、凭据类的区分、路由不在顺序内与全部冷却两种情形、冷却过期，以及推理强度的丢弃。其中一个组合用例同时挂载 retry 与 failover，并断言请求序列为 `['mock', 'mock', 'mock', 'other']` —— 即上文的顺序主张，经过验证而非假定。
